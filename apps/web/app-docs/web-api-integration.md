## Зафиксированный стык

- Браузер обращается к `/api/*` на адресе web. Next проксирует запросы на
  `API_INTERNAL_URL`: локально `http://127.0.0.1:3001`, в Compose `http://api:3001`.
  `NEXT_PUBLIC_API_URL` больше не используется. Внутренний адрес не содержит `/api`.
- Rewrites фиксируются при сборке Next. После изменения `API_INTERNAL_URL` нужно
  пересобрать web. В Compose это делает `./init.sh`.
- Авторизация — HttpOnly cookie `career_quest_session`, не Bearer token.
  `APP_ORIGIN` API должен точно совпадать с адресом браузера, включая схему и порт.
  `localhost` и `127.0.0.1` — разные origin. CORS для прямого доступа браузера к API
  на другом origin не настроен; приложение использует прокси.
- Источник типов — [OpenAPI JSON](../../api/openapi.json).
  Все 14 операций представлены в Orval-клиенте. Не редактировать generated-файл вручную.
- Импорт: `POST /api/hr/import` с `{employees_json, history_csv}` в JSON,
  не multipart. Оба поля обязательны; одно может быть пустой строкой. Импорт
  профиля не создает учетную запись для входа.
- Рекомендации и завершение принимают `{}`. После изменения цели или завершения
  обновлять profile, plan и recommendations; HR-агрегаты также могут измениться.
- `recommendations: []`, цель `null`, `mode: "rules"` и HTTP 503 для plan/chat —
  предусмотренные состояния. Readiness не является официальным порогом повышения.
- Отдельного endpoint записи на мероприятие нет. Не показывать неподключенную
  запись как успешную операцию.

## Порядок совместной работы

1. API сохраняет текущие operationId и схемы. При необходимом изменении сначала
   обновляет модели маршрутов, экспортирует `bun run openapi` из `apps/api` и
   описывает семантику в `docs/api-contract.md`.
2. Web выполняет `pnpm orval` из `apps/web`, проверяет diff клиента и реализует
   module API → query/mutation → UI по существующей Crystal Architecture.
3. Ближайший общий результат — рекомендации → завершение → пересчитанный профиль.
   Затем подключаются HR-сводка и импорт жюри. Новые API для этих стадий не нужны.
4. Перед передачей изменений: API typecheck/релевантные тесты, web typecheck и
   `lint:deps`, сборка, затем проверка через web origin. Успешный API healthcheck
   не подтверждает, что браузер использует свежую сборку и действующие маршруты.

## Запуск

`./init.sh` собирает и поднимает db, agent, api и web, затем открывает
`http://localhost:3000/ru/login`. Если 3000 уже занят локальным `pnpm start`,
можно запустить `WEB_PORT=3310 ./init.sh --no-open`; явный `APP_ORIGIN` в `.env`
при этом нужно согласовать с выбранным портом. Существующие пароли не меняются.

Для разработки web отдельно: запустить backend через `docker compose up --build -d --wait api`,
затем `pnpm dev` в `apps/web`. При измененном порте API задать соответствующий
`API_INTERNAL_URL` в `apps/web/.env.local` и перезапустить Next.

## Обнаруженные препятствия

При проверке на порту 3000 работала старая production-сборка: healthcheck API
возвращал 200, но `/ru/login` и `/ru/employee` возвращали 404. В исходной конфигурации
нового web отсутствовал proxy. Внесены proxy, общий Compose-запуск, исправление
namespace переводов профиля и удаление неиспользуемой template-мутации `updateUser`,
которой нет в Career Quest API.

Публичное развертывание и живые ответы OpenAI этой работой не подтверждаются.
