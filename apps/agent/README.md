# Career Quest Agent

Сервис на FastAPI для карьерных консультаций: рассчитывает дефициты навыков, подбирает до трёх мероприятий и отвечает сотруднику с помощью OpenAI. При недоступности модели возвращает результат по правилам.

**NestJS вызывает агент по REST и передаёт весь контекст при каждом запросе. Агент самостоятельно не запрашивает данные у NestJS.** Он не читает локальные файлы `data/`, не имеет базы сотрудников и не хранит историю диалога.

```text
Пользователь → NestJS → Python Agent → OpenAI (для чата и AI-подбора)
                │           │
                │           └─ расчёты и резервный подбор по правилам
                └─ данные, авторизация, история чата, сохранение выполнения
```

Авторизация, проверка доступа к данным сотрудника и HR-функции находятся на стороне NestJS. Сам агент не проверяет токены или права доступа. CORS регулирует браузерные запросы и не заменяет авторизацию.

## Быстрый старт

Нужен **Python 3.11+**: код использует `asyncio.timeout`. В Docker используется Python 3.12. Команды ниже рассчитаны на macOS/Linux и выполняются **из корня репозитория**.

1. Создайте окружение и установите зависимости:

```bash
python3 -m venv venv
venv/bin/pip install -r apps/agent/requirements.txt
```

2. Для AI-ответов добавьте в корневой `.env` строку `OPENAI_API_KEY=<ваш ключ>`. Если `.env` уже существует, дополните его; не перезаписывайте настройки других сервисов. Без ключа можно использовать подбор по правилам.

3. Запустите сервер:

```bash
venv/bin/uvicorn agent.main:app --app-dir apps --reload --port 8000
```

4. В другом терминале проверьте HTTP-сервис:

```bash
curl --fail-with-body http://localhost:8000/health
```

Ожидаемый ответ: `{"status":"ok"}`. Эта проверка **не проверяет ключ, модель или доступность OpenAI**.

Интерактивная документация доступна по адресу [localhost:8000/docs](http://localhost:8000/docs), схема — [localhost:8000/openapi.json](http://localhost:8000/openapi.json). Готовый запрос для первого обращения находится в разделе [Запрос от NestJS](#запрос-от-nestjs).

## Настройки

При локальном запуске `load_dotenv()` подхватывает корневой `.env`. Уже заданные переменные окружения имеют приоритет над значениями из файла. После изменения настроек перезапустите процесс.

| Переменная | Обязательность | Значение по умолчанию и поведение |
|---|---|---|
| `OPENAI_API_KEY` | Для AI-ответов | Без ключа сервис работает по правилам |
| `OPENAI_KEY` | Нет | Совместимое старое имя; используется, если `OPENAI_API_KEY` отсутствует или пуст |
| `OPENAI_MODEL` | Нет | В текущем коде — `gpt-6-astra`; укажите модель, доступную вашему API-проекту и совместимую с используемым структурированным ответом |
| `CORS_ORIGINS` | Нет | `http://localhost:3000`; несколько адресов разделяются запятыми |

Пример настройки CORS: `CORS_ORIGINS=http://localhost:3000,http://localhost:5173`. Для запросов NestJS → агент браузерный CORS не применяется.

Таймаут AI-попытки (8 секунд), число кандидатов (12) и отсутствие повторных запросов заданы в [openai_agent.py](openai_agent.py); переменных окружения для них сейчас нет. `/api/v1/advisor/plan` не обращается к OpenAI при любых настройках.

## Docker

Из корня репозитория собирайте образ с контекстом **только** `apps/agent`:

```bash
docker build -t career-agent apps/agent
docker run --rm -p 8000:8000 --env-file .env career-agent
```

Если нужен запуск без ключа и файла `.env`, используйте `docker run --rm -p 8000:8000 career-agent`.

Сервис слушает порт `8000` внутри контейнера и работает от непривилегированного пользователя. Корневой `.env` передаётся только при запуске и не попадает в образ. Для обращения из другого контейнера используйте имя сервиса или контейнера в общей сети Docker, а не `localhost`. Образ содержит только содержимое `apps/agent` и Python-зависимости; NestJS, фронтенд и `data/` в него не входят.

## HTTP API

Все POST-запросы принимают JSON с заголовком `Content-Type: application/json`.

| Метод и путь | Тело | Ответ | Вызов OpenAI |
|---|---|---|---|
| `GET /health` | — | `{"status":"ok"}` | Нет |
| `POST /api/v1/advisor/plan` | `{"context": ...}` | План по правилам | Нет |
| `POST /api/v1/advisor/recommendations` | `{"context": ...}` | Результат подбора | Если есть допустимые кандидаты |
| `POST /api/v1/advisor/chat` | `message`, `context`, необязательный `conversation_history` | Ответ, план и результат подбора | Попытка при каждом валидном запросе |

Для первичной отрисовки профиля используйте `/plan`, затем при необходимости загружайте AI-подбор отдельным запросом. Таймаут вызывающей стороны должен оставлять время на обработку контекста и передачу ответа сверх 8 секунд ожидания AI.

## Запрос от NestJS

Сохраните следующий синтетический пример в `chat-request.json` в текущем каталоге. Даты фиксированы для воспроизводимости примера; в рабочем запросе NestJS передаёт актуальную дату расчёта `as_of_date`.

```json
{
  "message": "Каких навыков мне не хватает и что пройти?",
  "conversation_history": [],
  "context": {
    "as_of_date": "2026-10-01",
    "employee": {
      "employee_id": "E0001",
      "full_name": "Сотрудник",
      "role": "Backend Engineer",
      "grade": "Junior",
      "skills": {"SK_PYTHON": 2},
      "career_goal": {"target_role": "Backend Engineer", "target_grade": "Middle"},
      "last_review_date": "2026-09-11",
      "preferred_language": "ru"
    },
    "skills": [
      {"skill_id": "SK_PYTHON", "name": "Python", "type": "hard"}
    ],
    "role_profiles": [
      {
        "role": "Backend Engineer",
        "grade": "Middle",
        "required_skills": {"SK_PYTHON": 3},
        "critical_skills": ["SK_PYTHON"]
      }
    ],
    "events": [
      {
        "event_id": "EV_101",
        "title": "Python Practice",
        "description": "Практический курс по Python",
        "type": "course",
        "format": "self_paced",
        "duration_hours": 4,
        "mandatory": false,
        "target_roles": ["Backend Engineer"],
        "target_grades": ["Junior", "Middle"],
        "develops_skills": [{"skill_id": "SK_PYTHON", "gain": 1, "max_level": 3}],
        "prerequisites": {},
        "upcoming_sessions": []
      }
    ],
    "activity_history": []
  }
}
```

Отправьте запрос:

```bash
curl --fail-with-body http://localhost:8000/api/v1/advisor/chat \
  -H 'Content-Type: application/json' \
  --data-binary @chat-request.json
```

Для `/plan` и `/recommendations` сохраните в отдельный `plan-request.json` только объект с полем `context` из примера, без `message` и `conversation_history`:

```bash
curl --fail-with-body http://localhost:8000/api/v1/advisor/plan \
  -H 'Content-Type: application/json' \
  --data-binary @plan-request.json
```

### Контекст и история

| Поле | Что передаёт NestJS |
|---|---|
| `context.as_of_date` | Дату расчёта в формате `YYYY-MM-DD` |
| `context.employee` | Одного сотрудника и снимок его навыков на дату оценки |
| `context.skills` | Каталог всех навыков, на которые ссылается контекст |
| `context.role_profiles` | Требования к ролям и грейдам, включая выбранную или автоматически предложенную цель |
| `context.events` | Каталог мероприятий, включая все мероприятия из истории |
| `context.activity_history` | Только записи выбранного сотрудника из `Dataset.history`; явно `[]`, если записей нет |
| `conversation_history` | Предыдущие реплики по порядку: от старых к новым, без текущего `message` |

`message` и `content` каждой реплики содержат от 1 до 3000 символов. В запросе допускается до 20 предыдущих реплик, модели передаются последние 12. Роли — только `user` и `assistant`:

```json
[
  {"role": "user", "content": "Хочу перейти на Middle."},
  {"role": "assistant", "content": "Какой формат обучения вам удобен?"}
]
```

Историю переписки сохраняет NestJS: идентификатора сессии и серверной памяти диалога у агента нет.

Передавайте мероприятия из истории, даже если они больше не доступны для записи: они нужны для анализа участия. Пустые значения CSV преобразуйте в `null` только для полей, допускающих `null`; для коллекций используйте `[]` или `{}` согласно схеме. ID новых профилей не ограничены диапазоном исходного набора. Неизвестные ссылки, дубликаты ID и уровни вне 0–5 отклоняются.

**Название поля истории — строго `activity_history`.** Текущая схема игнорирует неизвестные поля: `history` будет проигнорировано, а отсутствующее `activity_history` станет пустым списком. Аналогично не переданные `employee.skills` станут пустым словарём. При интеграции передавайте оба поля явно.

## Ответы API

### Подбор рекомендаций

Ответ `/recommendations` соответствует типу `Recommendations` из [контрактов TypeScript](../api/src/contracts.ts). Python-схемы находятся в [schemas.py](schemas.py).

| Поле | Значение |
|---|---|
| `mode` | `ai` при принятом выборе модели, `rules` при расчёте по правилам |
| `model` | Название использованной модели или `null` |
| `message` | Ответ консультанта или сообщение о подборе по правилам |
| `recommendations` | 1–3 карточки; пустой список, если допустимых шагов нет |
| `generated_at` | Время формирования в UTC |
| `duration_ms` | Время внутри функции подбора; не включает предшествующую валидацию контекста и создание `Advisor`, HTTP и сетевые задержки |

Карточка соответствует `Recommendation`: `event`, `score`, `factors`, `next_session`, `gains`, `in_progress`, `explanation`. В `factors` всегда четыре категории: `grade`, `gap`, `history`, `target`. Объяснение собирается из проверенных фактов. Модель выбирает ID и порядок шагов, а уровни навыков, доступность и факторы вычисляет Python. В версии 0.2 поля `event_id` и `title` карточки перенесены в `event`, общее `reason` заменено на `factors` и `explanation`.

Полный пример ответа по правилам для контекста выше **с `events: []`**. Время формирования и длительность приведены для иллюстрации:

```json
{
  "mode": "rules",
  "model": null,
  "message": "В каталоге нет доступного следующего шага, который сокращает оставшиеся дефициты.",
  "recommendations": [],
  "generated_at": "2026-10-01T10:00:00+00:00",
  "duration_ms": 1
}
```

Для исходного примера с `EV_101` подбор по правилам вернёт одну карточку: `event.event_id = "EV_101"`, `score = 1139.5`, `next_session = null`, прирост Python с 2 до 3 и четыре фактора. `null` у даты допустим для самостоятельного обучения.

Фрагмент этой карточки (поля `event`, `factors` и `explanation` здесь опущены):

```json
{
  "score": 1139.5,
  "next_session": null,
  "gains": [
    {"skill_id": "SK_PYTHON", "name": "Python", "before": 2, "after": 3, "target": 3}
  ],
  "in_progress": false
}
```

### План

Полный пример ответа `/plan` для того же контекста **с `events: []`**:

```json
{
  "employee_id": "E0001",
  "current_position": {"role": "Backend Engineer", "grade": "Junior"},
  "career_goal": {"target_role": "Backend Engineer", "target_grade": "Middle"},
  "goal_source": "explicit",
  "as_of_date": "2026-10-01",
  "last_review_date": "2026-09-11",
  "effective_skills": {"SK_PYTHON": 2},
  "counted_completions": [],
  "assessment_note": "Расчётный прогресс учитывает только completed_at после даты оценки и не позже as_of_date.",
  "readiness": 66.7,
  "projected_readiness": 66.7,
  "projected_skills": {"SK_PYTHON": 2},
  "trajectory": [],
  "gaps": [
    {
      "skill_id": "SK_PYTHON", "name": "Python", "current": 2,
      "required": 3, "gap": 1, "critical": true, "covered": false
    }
  ],
  "recommendations": [],
  "uncovered_skills": ["SK_PYTHON"],
  "mandatory_tasks": [],
  "warnings": []
}
```

`covered` означает наличие доступного кандидата для сокращения дефицита, а не полное закрытие навыка выбранным планом. `goal_source` принимает `explicit`, `next_grade` или `none`. Без цели `readiness` и `projected_readiness` равны `null`.

### Чат

Ответ `/chat` состоит из четырёх полей:

| Поле | Содержимое |
|---|---|
| `employee_id` | ID сотрудника из запроса |
| `reply` | Текст для отображения пользователю; совпадает с `recommendations.message` |
| `plan` | Полный план в формате выше, рассчитанный для выбранных шагов |
| `recommendations` | Полный объект результата подбора, включая `mode`, `model` и список карточек |

Карточки чата лежат в `recommendations.recommendations`. Их копия находится в `plan.recommendations`. Отдельный вызов `/plan` использует подбор по правилам, поэтому его шаги могут отличаться от шагов, выбранных моделью в чате.

## Ошибки и резервный режим

| HTTP | Ситуация | Действие клиента |
|---|---|---|
| `200`, `mode: "ai"` | Структурированный выбор модели принят | Показать ответ и карточки |
| `200`, `mode: "rules"` | Подбор без модели, нет кандидатов либо AI-попытка завершилась ошибкой | Показать результат по правилам; список может быть пустым |
| `422` | Нарушена схема, ссылки между данными или нет профиля целевой роли/грейда | Исправить контекст запроса |
| `500` | Необработанная ошибка сервиса | Обработать как сбой; резервный ответ не гарантирован для произвольных ошибок |

Режим `rules` не всегда означает сбой OpenAI: `/recommendations` с пустым набором кандидатов вообще не вызывает модель. Отсутствующий ключ, ошибка API, таймаут, отказ модели и невалидный выбор обрабатываются резервным подбором. `/plan` не содержит поля `mode` и всегда рассчитывается по правилам.

Пример `422` при отсутствии профиля выбранной цели:

```json
{"detail": "Нет требований для Backend Engineer / Middle"}
```

При ошибке Pydantic поле `detail` содержит **массив** ошибок с `loc`, `msg` и `type` (возможны дополнительные поля), а не строку. Клиент должен поддерживать обе формы.

## Как выбираются шаги

Сначала проверяются текущая роль и грейд, все prerequisites, даты, обязательность и история. Уже начатое и завершённое обучение исключается; клуб `EV_036` допускает повторы по правилу датасета. Цель по умолчанию — следующий грейд текущей роли, с `goal_source: "next_grade"`. Для Lead без цели автоматического повышения нет.

Подбор по правилам отдаёт приоритет критическим дефицитам через вес в оценке кандидата. Оценка складывается из:

- 1000 баллов за сокращение хотя бы одного критического разрыва;
- 100 × сумму закрываемых долей критических дефицитов и 40 × сумму долей всех дефицитов;
- до 6 баллов за завершённые похожие активности;
- штрафа за неявки, отказы и прекращение: 25 за попытку данного мероприятия и 10 за попытку другого мероприятия того же формата с общими навыками, суммарно не больше 120;
- поправки за длительность `min(10, duration_hours / 8)`.

Это явная политика ранжирования прототипа, а не вероятность успешного завершения или решение о повышении. История не запрещает повторную попытку и не трактуется как оценка мотивации сотрудника. Все использованные количества показываются в факторах.

OpenAI получает до 12 допустимых кандидатов с рассчитанными факторами и возвращает ID 1–3 шагов и текст ответа. Python проверяет ID, отсутствие повторов, критический приоритет первого шага и пользу каждого следующего шага после предыдущих. Числа и текст карточек вычисляются Python. Свободный текст `reply` генерирует модель; его фактическая корректность отдельной проверкой не подтверждается.

Таймаут всей AI-попытки — 8 секунд, повторных API-запросов нет; при обработанной ошибке используется результат по правилам. Это ограничивает ожидание AI, но не гарантирует время ответа всего HTTP-запроса: обработка контекста и сеть учитываются отдельно.

Модель получает карьерные факты, до 24 записей участия (сортировка по `date`; для отсутствующей даты используется `as_of_date`) и последние 12 реплик переписки. Расчёты по правилам используют всю историю, прошедшую фильтрацию по дате. Имя и ID сотрудника из профиля не включаются в подготовленные факты; текст переписки передаётся как получен и может содержать эти данные. Запрос выполняется с `store=False`; содержимое запроса всё равно передаётся внешнему API.

## Прогресс после выполнения

NestJS сохраняет `status: "completed"`, `completion_pct: 100` и `completed_at` в записи участия и повторно отправляет контекст. Повторное нажатие кнопки должно обновлять ту же запись `record_id`. `employee.skills` остаётся снимком последней оценки, а `effective_skills` — вычисленным результатом; не прибавляйте эффект одновременно к обоим.

В расчёт входят только завершения после `last_review_date` и не позже `as_of_date`. `completed_at` принимается как ISO-дата или ISO-время; сравнение с оценкой выполняется по дням. Записи без точной даты завершения и с неизвестной датой оценки не начисляют прирост. Предупреждения об этом находятся в `plan.warnings`. Для исторического CSV точный момент завершения восстановить нельзя.

`readiness` — процент покрытия требований: `100 × sum(min(level, required)) / sum(required)`. При наличии целевого профиля с нулевой суммой требований возвращается `100.0`, без целевого профиля — `null`. Это не вероятность повышения.

`projected_readiness`, `projected_skills` и `trajectory` моделируют выполнение шагов **в порядке ответа**, без согласования календаря. Прирост ограничен `gain` и `max_level` и никогда не снижает уже достигнутый уровень. Фактическое сохранение выполнения, права сотрудник/HR и агрегаты HR остаются в NestJS.

## Ограничения текущей версии

- **Календарь шагов не согласуется.** Для каждого мероприятия выбирается ближайшая сессия относительно `as_of_date`, без учёта дат предыдущих шагов. Поэтому прогноз не является готовым расписанием и может завышать достижимый результат при другом порядке посещения.
- **Временные зоны завершений не нормализуются.** Внутри одного дня `completed_at` сортируется как строка; разные смещения часового пояса могут изменить порядок начисления прироста. Завершения в день оценки не учитываются, поскольку сравнение с `last_review_date` выполняется по дням.
- **Чат связан с повторным подбором.** Каждый вопрос запускает выбор шагов заново. При наличии кандидатов ответ модели без выбранных ID отклоняется, даже если текст полезен для консультации.
- **Не строятся цепочки с разблокировкой новых курсов.** Подбор начинается с мероприятий, доступных при исходных эффективных навыках. Курс, входные требования которого выполнятся только после предыдущего шага, в текущую цепочку не добавляется.
- **Приоритет критических навыков в режиме правил задан весами.** Дополнительные 1000 баллов не являются абсолютной гарантией для произвольного каталога с большим числом некритических навыков. Для выбора модели первый критический шаг проверяется отдельно.
- **Контракт входа допускает неизвестные поля.** Опечатки могут быть проигнорированы; особенно важны явные `activity_history` и `employee.skills`. План пока возвращается как словарь без отдельной Pydantic-модели ответа, поэтому его структура описана в README подробнее, чем в OpenAPI.
- **Нет собственной авторизации и хранения данных.** Агент принимает контекст от доверенного вызывающего сервиса; проверку доступа и сохранение результата обеспечивает NestJS.

## Частые проблемы

| Симптом | Что проверить |
|---|---|
| Всегда `mode: "rules"` | Есть ли кандидаты, задан ли ключ, доступна ли выбранная модель; укладывается ли AI-попытка в 8 секунд. Причиной также бывает отклонённый выбор модели |
| `/health` работает, но AI не отвечает | Health проверяет только HTTP-сервис. Ключ и доступ к модели проверяются при попытке AI-подбора |
| Пустой список рекомендаций | Задана ли цель, есть ли подходящие роль/грейд, выполнены ли `prerequisites`, остались ли дефициты. Для `online` и `offline` нужны сессии не раньше `as_of_date`; обязательные, начатые и обычно завершённые активности исключаются |
| `422` с сообщением об отсутствующем мероприятии или навыке | Включены ли в каталоги все ID, используемые профилем, требованиями, мероприятиями и историей |
| `422` с сообщением об отсутствии требований | Есть ли профиль для явной цели либо следующего грейда текущей роли |
| Завершение не изменило навыки | Переданы ли `last_review_date` и `completed_at`, завершение строго после оценки и не позже `as_of_date`, не достигнут ли `max_level`. Посмотрите `plan.warnings` и `counted_completions` |
| Рекомендуется уже пройденный курс | Передана ли запись в `activity_history` со статусом `completed`, верны ли ID и даты; `EV_036` допускает повторы |
| `ModuleNotFoundError: agent` | Запускаете ли из корня репозитория с `--app-dir apps`; для тестов нужен `PYTHONPATH=apps` |
| NestJS в контейнере не видит агент | Находятся ли контейнеры в одной сети; используйте имя контейнера/сервиса и порт `8000`, а не `localhost` |

Обработанные причины перехода на правила записываются логгером `agent.openai_agent` на уровне `INFO` как `Recommendation rules fallback: <класс исключения>`. Для просмотра нужен вывод этого логгера на уровне `INFO`; подробного кода причины и текста ошибки провайдера сейчас нет.

## Структура и тесты

| Файл | Ответственность |
|---|---|
| [main.py](main.py) | FastAPI, CORS, маршруты и преобразование ошибок контекста в HTTP |
| [schemas.py](schemas.py) | Схемы запросов и рекомендаций, валидация ссылок |
| [advisor.py](advisor.py) | Допуск к мероприятиям, расчёт навыков, ранжирование и план |
| [openai_agent.py](openai_agent.py) | Подготовка фактов, вызов модели, проверка выбора и резервный режим |
| [requirements.txt](requirements.txt) | Диапазоны версий зависимостей; lock-файла пока нет |
| [Dockerfile](Dockerfile) | Сборка и запуск только Python-сервиса |
| [tests/test_advisor.py](tests/test_advisor.py) | Тесты расчётов, AI-сценариев с подменой клиента и HTTP-контракта |

Запуск существующих тестов из корня репозитория после установки зависимостей:

```bash
PYTHONPATH=apps venv/bin/python -m unittest discover -s apps/agent/tests -v
```

Тесты покрывают ловушку из ТЗ (критический навык против короткой активности по слабому навыку), пропуски и отказы, ограничения допуска, прирост после выполнения, проверку ответа модели, таймаут и REST-контракт. OpenAI подменяется в тестах; реальных API-вызовов нет.
