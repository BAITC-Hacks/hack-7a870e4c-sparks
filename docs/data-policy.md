# Расчёты и политика работы с данными

Это описание правил MVP в сервисах `apps/api/src/modules/employees/`, `apps/api/src/utils/dataset/`, `apps/api/src/modules/recommendations/`, Python-агенте `apps/agent/` и хранилище `apps/api/src/utils/db/index.ts`. Данные сохраняются в PostgreSQL через Prisma. Формулы прогресса, ранжирования и демонстрационное подтверждение завершения — проектные решения команды, а не официальные пороги повышения или методика оценки Организатора. Исходные ограничения датасета приведены в `case_1/career_quest_dataset/README.ru.md`.

## Дата среза и исходная оценка

Все расчёты используют `meta.as_of_date` из исходных файлов; сейчас это `2026-10-01`. Даты метаданных сотрудников, мероприятий и навыков должны совпадать. Системная дата компьютера не меняет доступность сессий или историю. При импорте другая дата среза не принимается. Изменение даты и миграция набора в интерфейсе MVP не реализованы.

`employee.skills` — базовая оценка на `last_review_date`. Пропущенный навык при вычислении требований, prerequisites и прироста имеет уровень 0. Базовые уровни — целые числа от 0 до 5. Исходные оценки сохраняются отдельно от вычисленных `effective_skills`.

В расчёт прироста входят только записи `status=completed` с известным `completed_at`. История фильтруется по `date <= as_of_date`, а завершения обрабатываются по времени `completed_at`; при одинаковом ключе используется `record_id`.

- Исходная история без `completed_at` не начисляет прирост независимо от даты участия. `date` не является точной датой завершения и не подставляется вместо неё. Профиль показывает предупреждение о возможном недоучёте навыков. История сохраняется и влияет на допустимость повторного участия.
- День `completed_at` должен быть строго позже `last_review_date` и не позже `as_of_date`. Завершения в день оценки, до оценки и после даты среза не начисляются. API и Python-агент используют одинаковую границу по дням.
- При повторных записях завершения одного мероприятия после оценки его прирост учитывается один раз. Исключение — клуб `EV_036`: отдельные записи `record_id` могут добавить прирост повторно. Дедупликация расчёта не удаляет исторические записи, включая ежегодные обязательные повторы.

Каждый прирост рассчитывается отдельно для соответствующего навыка:

```text
новый_уровень = max(текущий_уровень,
                   min(текущий_уровень + gain, max_level, 5))
```

`max_level` ограничивает прибавку конкретного мероприятия и никогда не уменьшает уже имеющийся уровень. Незавершённые статусы, проценты выполнения, оценки тестирования и обратная связь не добавляют уровней навыка. Расчёт начинается заново от базовой оценки и сохранённой истории, поэтому простое повторное чтение профиля не накапливает прирост.

## Цель, разрывы и процент покрытия

Явная `career_goal` задаёт целевую пару роли и грейда. Без неё берётся следующий грейд текущей роли в порядке Junior → Middle → Senior → Lead. У Lead без явной цели следующей ступени нет: `target=null`, `readiness=null`, список рекомендаций пуст, причина показана пользователю. Изменение цели не меняет фактическую роль и грейд сотрудника.

Для каждого навыка целевого профиля:

```text
разрыв = max(0, требуемый_уровень - текущий_уровень)
покрытие, % = 100 × сумма min(текущий_уровень, требуемый_уровень)
                   / сумма требуемых_уровней
```

Процент округляется до одного десятичного знака. Если целевой профиль есть, но сумма его требований равна нулю, покрытие равно 100%; если профиля требований нет, значение отсутствует. Уровень выше требования не компенсирует недостаток другого навыка. Критические навыки в этой формуле не имеют дополнительного веса. Процент — визуальный ориентир полноты требований; достижение 100% не присваивает новый грейд и не подтверждает право на повышение.

В `gaps` остаются только положительные разрывы. Они сортируются сначала по критичности, затем по размеру разрыва и идентификатору навыка. В профиле API `covered=true` означает, что в каталоге существует добровольное мероприятие с положительным приростом и `max_level` выше текущего уровня. Это ещё не гарантирует доступность сотруднику: аудитория, prerequisites, история и даты проверяются отдельно. Если максимальный уровень каталога ниже целевого, профиль показывает ограничение. В плане Python-агента `gaps[].covered` имеет более узкий смысл: навык сокращает хотя бы один уже допустимый для сотрудника кандидат. Поэтому эти флаги могут различаться при одинаковых уровнях и разрывах. Для `SK_TEST_DESIGN` мероприятия не выдумываются.

## Допустимые следующие шаги

Основной путь API передаёт контекст выбранного сотрудника Python-агенту: `/api/v1/advisor/recommendations` для подбора, `/api/v1/advisor/plan` для плана без OpenAI и `/api/v1/advisor/chat` для консультации. API проверяет права до обращения к агенту. Базовые навыки и история передаются раздельно; вычисленные `effective_skills` не подставляются вместо исходной оценки.

Общие ограничения Python-агента и резервного расчёта API исключают мероприятие, если выполняется хотя бы одно условие:

1. `mandatory=true`.
2. Текущая роль или грейд не входят в аудиторию `target_roles` / `target_grades`.
3. Добровольное мероприятие уже завершено. Исключение — повторяемый `EV_036`; его повтор разрешён, если нет завершения в текущую дату среза.
4. Хотя бы один prerequisite выше эффективного уровня навыка.
5. Для online/offline нет сессии с датой не раньше `as_of_date`. Для self-paced список сессий не требуется.

Смена карьерной цели не обходит фильтр фактической аудитории. Для кандидата требуется хотя бы один реальный прирост, сокращающий разрыв целевого профиля. Ближайшая сессия — минимальная подходящая дата; self-paced не требует сессии.

Python-агент также исключает мероприятия с участием `in_progress` или `overdue`: он подбирает новые шаги. `gains` его карточки содержит прирост только по дефицитным навыкам цели. После каждого выбранного шага агент применяет весь эффект мероприятия и пересчитывает пользу следующего. Второй шаг не выбирается, если после первого он уже не сокращает разрыв. В последовательность входят до трёх разных мероприятий из исходно допустимого набора; занятия, открывающиеся только после выполнения prerequisites в будущем, в эту подборку не добавляются.

Ранжирование Python-агента:

- 1000 баллов за сокращение хотя бы одного критического разрыва;
- 100 × сумма закрываемых долей критических дефицитов и 40 × сумма долей всех сокращаемых дефицитов;
- по 2 балла за завершённое такое же мероприятие или похожее мероприятие того же формата с общими навыками, суммарно до 6;
- штраф 25 за неявку, отказ или прекращение данного мероприятия и 10 за такое участие в похожем мероприятии того же формата, суммарно не больше 120;
- вычет `min(10, duration_hours / 8)` за длительность.

Баллы могут быть отрицательными; это политика выбора прототипа, а не оценка сотрудника или вероятность успеха. История не запрещает новую попытку после отказа или прекращения. Факторы показывают использованные количества и напоминают, что причины пропусков неизвестны. При равном балле используются ближайшая сессия и `event_id`. Если есть допустимый кандидат по критическому разрыву, первый шаг должен сокращать такой разрыв.

OpenAI получает до 12 кандидатов и выбирает их ID и порядок. Python проверяет результат, рассчитывает уровни и формирует объяснения из четырёх категорий факторов: роль/грейд, разрыв, история и цель. Отсутствие ключа, таймаут OpenAI до 8 секунд, ошибка или недопустимый выбор модели включают `mode: "rules"` внутри Python-агента с теми же правилами допуска и последовательного прироста.

## Резервный расчёт при недоступности агента

API ожидает весь ответ Python-агента, включая чтение тела, не более 9 секунд. При ошибке связи, таймауте или ответе, не прошедшем проверку, endpoint рекомендаций возвращает локальный расчёт `candidatesFor` с `mode: "rules"` и сообщением «Расчетный режим API». Отсутствующий адрес агента также включает этот резервный путь. Это отдельный режим с более простой политикой; одинаковый `mode: "rules"` у агента и API не означает одинаковый список шагов. `/plan` и `/chat` при недоступности агента возвращают `503`; локальный ответ консультанта для них не выдумывается.

Резервный API может предложить продолжить уже начатое мероприятие. Его балл кандидата:

```text
балл = сумма(сокращение_разрыва_навыка × вес_навыка)
вес_навыка = 2 для critical_skills целевого профиля; иначе 1
```

Сокращение ограничивается требуемым уровнем навыка. При равном балле сначала идёт уже начатое мероприятие, затем более короткое по `duration_hours`, затем по `event_id`. История отказов и прекращения здесь описывается фактором без штрафа в балле. Выбираются первые три кандидата. Прирост каждой карточки рассчитан независимо от других относительно текущих навыков, включая полезные эффекты вне целевых дефицитов; суммировать `gains` нескольких резервных карточек нельзя. Этот расчёт не гарантирует критический первый шаг и не устраняет перекрывающиеся приросты так, как Python-агент.

API проверяет контракт ответа агента, уникальность и допустимость мероприятий, соответствие каталогу и не менее трёх категорий факторов. Python отвечает за последовательную арифметику и выбор модели. Реализация границы находится в `apps/api/src/modules/recommendations/service.ts`. Если кандидатов нет, возвращается пустой список с объяснением. Внешние или вымышленные занятия не добавляются автоматически.

## Подтверждение завершения в MVP

Кнопка завершения моделирует результат активности и не подтверждает реальное прохождение обучения, посещение сессии или выдачу сертификата. Сервер повторно проверяет допустимость активности по текущему состоянию. Для online/offline используется наличие доступной будущей сессии; отдельного бронирования и проверки фактического посещения в MVP нет.

Новая запись получает `date=as_of_date`, `status=completed`, `completion_pct=100`, `assigned_by=self`, пустые score/feedback/due_date и новый `record_id`. `completed_at` фиксируется как `as_of_dateT12:00:00.000Z`. Это время виртуального демонстрационного дня, а не показание реальных часов.

Если есть начатое участие, обновляется последнее по дате; иначе используется существующая запись этого мероприятия за дату среза, если она есть. Её ID и исходная дата участия сохраняются. У ранее существовавшей записи поля оценки, обратной связи и назначения сохраняются.

Повторное подтверждение завершённой добровольной активности возвращает `already_completed=true` без нового прироста. Для `EV_036` подтверждение допускается один раз за виртуальный день; повторный запрос в тот же день также идемпотентен. Новые обязательные активности через этот сценарий не создаются. Их исторические записи, включая ежегодные compliance-повторы, сохраняются при импорте и видны в профиле/HR-аналитике.

Сохранение и перерасчёт выполняются в транзакции Prisma в PostgreSQL. Изменённые навыки, разрывы и последующие кандидаты вычисляются по сохранённой истории. Повторный запуск API не перезаписывает заполненную БД исходным датасетом.

## Импорт профилей и истории

Импорт доступен только HR. API принимает JSON-объект с массивом `employees` и/или CSV исходного формата; один из файлов может быть пустым. Общий размер содержимого ограничен 8 МиБ. При наличии `meta` его `as_of_date` должен совпадать с текущей датой среза. Мероприятия, роли и навыки из этих файлов не импортируются.

Обязательные CSV-колонки: `record_id,employee_id,event_id,date,due_date,status,completion_pct,score,feedback_rating,assigned_by`. Дополнительно разрешена колонка `completed_at` в формате UTC `YYYY-MM-DDTHH:mm:ss.sssZ`. Пустые необязательные числовые поля и due_date становятся `null`. Неизвестные или повторяющиеся CSV-колонки отклоняются.

Профиль с существующим `employee_id` заменяется целиком, а запись истории с существующим `record_id` обновляется целиком; это не частичный patch. Другие записи сохраняются. Числа в ответе импорта показывают количество принятых строк/профилей, включая обновления. Повторная загрузка одинаковых ID не создаёт новых копий. Замена базовой оценки или истории может закономерно изменить вычисленные навыки; импорт следует рассматривать как обновление исходных данных.

Проверяется весь объединённый набор до записи: типы и диапазоны значений, реальные календарные даты, известные роли/грейды/навыки, ссылки на сотрудников, руководителей и мероприятия, соответствие статусов процентам, допустимость score/due_date/overdue/no_show, корректность времени завершения. Дубликаты ID внутри одного файла и одинаковые участия `employee_id + event_id + date` отклоняются. Повтор добровольной активности после завершения запрещён, кроме `EV_036`; обязательные повторы сохраняются. При ошибке ни один профиль или ряд истории из запроса не сохраняется.

Новые профили доступны HR сразу. Сам запрос импорта не создаёт пароль, не меняет роли аккаунтов и не открывает сотрудникам чужие профили. Учётные записи выдаются отдельно административным инструментом; при последующем запуске API отсутствующие аккаунты также создаются из серверной конфигурации. Секреты и индивидуальные пароли не входят в импортируемые файлы и Git.

## HR-агрегации и границы применения

HR видит число сотрудников, сотрудников без допустимого следующего шага с причиной, количество сотрудников с каждым дефицитом и средний положительный разрыв по ним, округлённый до двух знаков. Наличие следующего шага в HR-агрегации рассчитывает локальный `candidatesFor`, поэтому начатое обучение может считаться доступным продолжением, хотя Python-агент не предлагает его как новый шаг. Участие по мероприятиям агрегируется в completed, in_progress и остальные статусы. Считаются записи участия, а не уникальные люди: повторяемое мероприятие может увеличить счётчик несколько раз. Обязательные мероприятия включены в эту историю, но исключены из рекомендаций.

Сотрудник получает собственный профиль и не имеет доступа к списку чужих профилей, их вовлечённости, HR-обзору и импорту. Публичных рейтингов результативности нет. Все исходные и демонстрационные данные синтетические; использование реальных персональных данных не предусмотрено и запрещено условиями выбранного кейса.
